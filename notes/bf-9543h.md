## What "bug default priority" means here

When a user runs `bf create --type bug --title "..."` **without** `--priority`, the resulting
bug should get the default priority **P2 (Medium)** — the same default as every other issue
type. Bugs are not special-cased; they inherit the same default as task/epic/feature/etc.

The default comes from clap's `--priority` arg declaration (`src/cli/mod.rs:49`):

```rust
/// Priority (0=Critical, 4=Backlog)
#[arg(long, default_value = "2")]
priority: i32,
```

…which `cmd_create` applies directly via `issue.priority = Priority(priority);`
(`src/cli/mod.rs:1099`). At the model level, `Priority::default()` returns `Self::MEDIUM`
(`src/model.rs:142-143`), and `Priority::MEDIUM = Self(2)` (`src/model.rs:150`), so every code
path that falls back to the default converges on P2.

## Finding: config `default_priority` is NOT wired into `bf create`

`config.yaml` has a `default_priority` key (default `2`, written by `bf init`). It is read
only by the `bf config get/set` subcommand — **never by `cmd_create`**. The create command's
default comes entirely from clap's hardcoded `default_value = "2"`.

Demonstrated empirically in the temp workspace:

```bash
sed -i 's/^default_priority:.*/default_priority: 4/' .beads/config.yaml
bf create --type bug --title "Config Override Bug"   # → still Priority: P2, not P4
```

Confirmed identical for bugs as for epics (see `notes/bf-3mvas.md`). So `default_priority` is
effectively decorative for the interactive `bf create` command — a user who changes it in
config (or via `bf config set default_priority 4`) and then omits `--priority` will be
surprised that new bugs still come out as P2. This is a pre-existing latent inconsistency, not
a regression, and out of scope for this verification bead — flagging for awareness (same
finding already tracked in `notes/bf-3mvas.md`).
