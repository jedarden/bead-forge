# bf-38f4 — "Fix JSON formatter to output array instead of JSONL"

**Outcome: NOT implemented — bead left open (status: blocked) for human adjudication.**

The task as written asks to change `bf list --format json` (and by extension
`ready`/`search`/`recent`) from JSONL to a JSON array, justified as
"Array format matches br's output for compatibility." Investigation shows this
premise is **false** and the change would **violate the documented spec, break
deliberate test coverage, and provide zero functional benefit.** This is the
needle-dispatched anti-pattern already called out in memory
`bf-json-output-format.md` ("Needle-dispatched beads sometimes get this
backwards: 'bf outputs JSON arrays, not JSONL' — that's only true for `show`;
the listing commands are JSONL").

## Why the premise is false

The task claims an array "matches br's output for compatibility." But `br` is a
**delegating shim**, not a separate binary:

- `~/.local/bin/br` (confirmed) is `#!/bin/sh` … `exec "$HOME/.local/bin/bf" "$@"`
- `docs/README.md` §"`br` produces byte-identical output" (lines 356–364):
  "`br` delegates to the `bf` binary … every `br` command emits **byte-identical**
  output to its `bf` equivalent — same JSONL, same array wrapping for `show` …"
- The compatibility contract is therefore `br == bf`, **both JSONL** for listings.
  There is no external `br` emitting arrays that `bf` must "match" — changing `bf`
  would make *both* emit arrays and thereby *break* the documented
  `br list --format json == bf list --format json` round-trip (README line 391),
  not satisfy it.

## Why JSONL is the deliberate, current design (verified)

1. **Live behavior** — `bf list --format json` on this workspace today emits one
   compact JSON object per line (JSONL), no array wrapper.
2. **`src/format/json.rs` `format_issues()`** — `.join("\n")` with doc comments
   explaining the `assignee`/`labels` display normalization for downstream
   consumers of `list`/`ready`/`search --format json`.
3. **`docs/README.md` §"Listing commands emit JSONL — not a JSON array"**
   (lines 282–328) — the documented spec explicitly says listing commands emit
   JSONL with no array wrapper, parse line-by-line, and `ready` alone
   special-cases emptiness to `[]`.
4. **`tests/bf_520v_json_format.rs`** — dedicated integration test *pins* JSONL,
   including `assert!(serde_json::from_str::<Value>(&out).is_err())` asserting the
   concatenated output is NOT a single JSON value. Plus unit tests in
   `json.rs` (`format_issues_multiple_yields_jsonl_one_object_per_line`, etc.).
5. **`show` is the deliberate array exception** (README §"bf show emits a one-element
   array"), to stay parse-compatible with NEEDLE's `parse_single_bead`.

## The change provides no functional benefit

NEEDLE's consumer — `NEEDLE/src/bead_store/mod.rs:744 parse_beads` — already
**accepts both** shapes: it tries a JSON array first
(`serde_json::from_str::<Vec<Bead>>`) and falls back to JSONL line-by-line.
Today it parses fine via the fallback; emitting arrays would just satisfy the
first branch. No bug is fixed.

## Cost of making the change (why it was declined)

- Contradicts the documented command spec (`docs/README.md`).
- Requires deleting/rewriting `tests/bf_520v_json_format.rs` and the JSONL unit
  tests in `src/format/json.rs` (working, deliberate coverage).
- Invalidates the verified memory note `bf-json-output-format.md`.
- Risks breaking any other JSONL-line-by-line consumer or `jq -s` pipeline.

## Recommendation

If arrays for listings are genuinely desired, it is a **spec change** that must be
made deliberately and end-to-end: update README §"Listing commands emit JSONL",
the `br == bf` compatibility contract, `tests/bf_520v_json_format.rs`, the
`json.rs` unit tests, and the memory note together — not as an isolated "fix."
Absent that intent, **keep JSONL** and close this bead as won't-do.

No production code changed. (Only this notes file was added.)
