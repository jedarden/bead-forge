# Fix Plan: --limit 0 Handling (bf-217m)

## Status: **ALREADY IMPLEMENTED**

The fix for `--limit 0` handling has already been implemented in `src/claim.rs`. This document confirms the design approach and implementation.

## Problem Statement

When using `bf ready --limit 0`, the command should return **all** ready beads (unlimited), not zero beads. SQLite's `LIMIT 0` returns an empty result set, which is incorrect behavior for this use case.

## Design Decision

**Decision: Omit LIMIT clause entirely when limit == 0**

### Rationale

1. **SQLite LIMIT semantics**: `LIMIT 0` in SQL returns zero rows, not unlimited rows
2. **No LIMIT -1 support**: SQLite does not support `LIMIT -1` as an unlimited indicator
3. **Omission is clearest**: Omitting the LIMIT clause entirely is the most explicit way to express "unlimited"
4. **Performance**: No unnecessary parameter binding or conditional logic in SQL execution

### Rejected Alternatives

| Alternative | Reason for Rejection |
|-------------|---------------------|
| `LIMIT -1` | SQLite does not support negative LIMIT values |
| `LIMIT 9223372036854775807` | Magic number, unclear intent, potential integer overflow |
| Always limit and fetch more | Adds complexity, no clear benefit |

```rust
#[test]
fn test_get_ready_candidates_limit_zero_returns_all() {
    let (_temp, mut storage) = setup_test_db();

    // Create 15 open beads
    for i in 0..15 {
        let issue = Issue::new(
            format!("bf-{:0>4}", i),
            format!("Test bead {}", i),
            ".".to_string(),
        );
        storage.create_issue(&issue).unwrap();
    }

    // limit=0 means unlimited - omit LIMIT clause in SQL
    let candidates = storage
        .with_immediate_transaction(|tx| get_ready_candidates(tx, 0, None, None))
        .unwrap();

    // All 15 beads should be returned (unlimited behavior)
    assert_eq!(candidates.len(), 15, "Expected all 15 beads to be returned with limit=0");
}
```
