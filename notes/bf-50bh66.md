# Structural Differences: Expected vs Actual Batch Operations Format

**Task:** Document structural differences between expected and actual formats.

**Dependencies:**
- Expected format documented in `notes/bf-2lfh5z.md`
- Actual format documented in `notes/bf-1dzcxb.md`

---

## Executive Summary

The test expects **output to contain bead data** (created beads with fields like `priority`, `labels`), but the actual implementation produces **operation metadata** (results with fields like `status`, `id`, `error`, `message`). This is a **fundamental structural mismatch**.

---

## 1. Envelope Structure Differences

### Expected Envelope
```json
{
  "data": [...]
}
```
- **Single field:** Only `data` key present
- **No versioning:** No `version` or `kind` fields

### Actual Envelope
```json
{
  "version": 1,
  "kind": "batch",
  "data": [...],
  "warning": null
}
```
- **Multiple fields:** `version`, `kind`, `data`, `warning`
- **Versioned:** Includes `version: 1` for compatibility
- **Typed:** Includes `kind: "batch"` to identify command type
- **Warning support:** Optional `warning` field for auto-flush failures

**Impact:** Test can parse the actual envelope (looks for `data` array), but the envelope structure is more complex than expected.

---

## 2. Array Element Structure (Root-Level Mismatch)

### Expected: Bead Objects
The test expects `data` array to contain **bead objects**:

```json
"data": [
  {
    "priority": 0,
    "labels": ["critical", "batch"],
    // ... other bead fields
  }
]
```

**Purpose:** Verify the beads that were created
**Fields present:** Bead data (priority, labels, etc.)
**Source:** Bead store/database records

### Actual: BatchResult Objects
The implementation returns **operation result objects**:

```json
"data": [
  {
    "op": 0,
    "status": "ok",
    "id": "bf-abc123",
    "error": null,
    "message": "Created bead bf-abc123"
  }
]
```

**Purpose:** Report whether each operation succeeded
**Fields present:** Operation metadata (index, status, ID, message)
**Source:** Operation execution results

**Impact:** **This is the core issue.** The test cannot access bead fields because the output contains operation results, not bead data.

---

## 3. Map vs Sequence Structure

### Expected Behavior
- **Input:** JSON array of operations
- **Output:** JSON array of beads created by those operations

**Flow:** Operations → Beads → Output beads

### Actual Behavior
- **Input:** JSON array of operations
- **Output:** JSON array of operation results

**Flow:** Operations → Results → Output results

**Impact:** The actual implementation follows the pattern of "operation result reporting," not "bead data retrieval."

## 7. Root Cause Analysis

The structural mismatch stems from **different mental models**:

### Test Mental Model
*"I run a batch command to create beads, and I want to see the beads that were created."*
→ **Query-oriented:** Output = query result for created beads
→ **Parallel to:** `SELECT * FROM beads WHERE ...`

### Implementation Mental Model
*"I run a batch command, and I want to know if each operation succeeded."*
→ **Action-oriented:** Output = operation execution report
→ **Parallel to:** CLI exit codes or HTTP response status

## 8. Implications

### For the Test
- ❌ Cannot access bead fields from output
- ❌ Cannot verify `priority` values
- ❌ Cannot verify `labels` arrays
- ❌ Cannot count created beads by checking array length

### For the Implementation
- ✅ Consistent with other CLI batch operations (report success/failure)
- ✅ Follows standard patterns for operation result envelopes
- ✅ Supports error reporting per operation
- ❌ Does not support the test's validation approach

---

## 9. Possible Resolution Paths

This is NOT just a formatting issue—it's a **design question** about what `bf batch --format json` should return:

### Option A: Change the test
- Rewrite test to validate operation results instead of bead data
- Verify success/failure, bead IDs, and error messages
- Use separate `bf list` command to retrieve bead data for validation

### Option B: Change the implementation
- Return bead data in `data` array (what test expects)
- Move operation results to a different envelope field (e.g., `results`)
- Breaks consistency with other batch-style commands

### Option C: Hybrid approach
- Add optional flag to return bead data instead of operation results
- Example: `bf batch --format json --output-beads`
- Maintains backward compatibility while supporting test's use case

---

## 10. Conclusion

The structural differences are **fundamental and systemic**:

1. **Envelope structure:** Expected minimal, actual versioned and typed (manageable)
2. **Array element type:** Expected bead data, actual operation metadata (critical)
3. **Field content:** Expected bead fields, actual result fields (critical)
4. **Purpose:** Expected verification of created beads, actual reporting of operation success (critical)

The test and implementation are **structurally incompatible**—not just differing in field names or envelope details, but in what the output fundamentally represents.
